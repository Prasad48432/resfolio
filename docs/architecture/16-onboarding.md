# 16 — Onboarding & Resume Import

**Status:** Accepted — implemented 2026-07-30.
**Depends on:** [01](01-profile-engine.md), [08](08-dashboard-ux.md),
[10](10-auth-and-security.md), [13](13-ai-layer.md).
**Constrains:** what a new account sees before it sees the dashboard; where
résumé extraction lives; the `profiles.onboarding_completed` gate.
**Closes:** the "Resume import / onboarding" deferred design in
[docs/README.md](../README.md).

---

## Problem Statement

Until now, signing in for the first time landed a user on `/profile`, in the app
shell, in front of a seeded profile containing "Example Company", "Your most
recent role" and a skills group reading `Add · your · skills`.

Every individual decision behind that screen was right. The seed exists because
doc 08 says empty states should teach rather than confront. The editor is the
product's default screen because the Profile is the source of truth. The shell
is there because the shell is always there.

The problem is what they add up to on the one visit that decides whether someone
comes back. A new user arrives holding a document that already contains their
entire career — everyone has a résumé — and the product's answer is a form with
nine sections and a sidebar offering eight more screens that are also empty. The
work of getting started is entirely theirs, and it is an hour of typing they have
already done once.

This is the activation problem, and it has a specific shape here: **Resfolio's
value is proportional to how complete the Profile is.** A half-filled profile
produces a bad resume, an embarrassing portfolio, a job match that reports gaps
that are really just omissions, and an AI conversation with nothing to work
with. Every downstream feature in docs 02–13 is a function of this one document
being filled in, so the cost of a user stopping at 20% complete is not 20% of the
product — it is most of it.

Two things follow, and this document decides both:

1. **A first run needs its own screen**, outside the workspace, asking one
   question.
2. **The résumé is the fastest possible path to a complete Profile**, and reading
   one is a job for the AI layer that already exists.

## Proposed Architecture

### 1. The flag, and where it lives

`profiles.onboarding_completed boolean not null default false` (migration
`0018`, which backfills existing rows to `true`).

**It is on `profiles`, not on `user`, and the reason is the session cookie
cache.** Adding it to the Better Auth user model would have been the obvious
route — `additionalFields` in the auth config, regenerate `schema/auth.ts`, read
it off the session with no extra query. That last part is exactly the problem.
Doc 10 configures a **five-minute signed cookie cache** over DB sessions, so a
field on `user` is served from the cookie for up to five minutes after it
changes. A user who finishes onboarding would be redirected back into it by the
gate, repeatedly, for five minutes, on every navigation — and the bug would be
invisible in development, where nobody waits five minutes between clicks.

Three lesser reasons agree with it. `schema/auth.ts` is generated by the Better
Auth CLI and may not be hand-edited (doc 10). Onboarding is about profile
_content_ — this is the row it pre-fills. And `profiles.user_id` is unique, so
the two homes are 1:1 either way; this picks the one that is semantically true.

**An absent profile row reads as "not onboarded."** The row is created on first
access, so its absence is the truest available answer rather than a convenient
default.

### 2. The gate, in two halves that never point at each other

- **Forward.** The `(dashboard)` layout — the one place every authenticated
  screen passes through — redirects to `/onboarding` while the flag is false. One
  indexed single-column read per navigation (`isOnboardingComplete`), and it
  **does not write**: a gate that seeds a profile as a side effect of asking a
  question would create a row for a user it is about to send elsewhere.
- **Backward.** The `(onboarding)` layout redirects a completed user to
  `/profile`. Onboarding is not re-enterable: it is not a settings screen, and a
  finished user reaching that URL from history should not be offered a flow that
  replaces their profile.
- The login page resolves the same question at the OAuth callback's landing point,
  which saves a brand-new user a visible bounce through a shell they are about to
  be redirected out of.

The two gates are **complementary conditions on the same boolean**, which is
what keeps this out of the redirect loop `/login` had to be designed around
(doc 10). `proxy.ts` is untouched: it is edge-resident and database-free by
design, and this decision needs a row.

### 3. Its own route group, `(onboarding)`

Not inside `(dashboard)`. The app shell is a workspace — nine destinations, a
command palette, a top bar naming your section — and every piece of that is
furniture for someone who already has a profile. A first-run flow inside it
offers a brand-new user navigation to eight empty screens.

`/onboarding` is full-viewport and has almost no chrome: a wordmark that is not a
link, because the only exits are the two decisions the screen is asking for. It
mounts `ThemeProvider` itself, following the dashboard's rule that theming is
scoped to the authenticated tree — a user arriving from a dark-themed dashboard
should not meet one light screen in the middle of the product. It does not use
`card-surface`; that stays `/login`'s and `apps/web`'s one brand moment.

### 4. Step 1: two options and an exit

- **Upload your résumé (primary).** A dashed drop zone over a real
  `<input type="file">` — hidden but focusable, with the visible card as its
  label, so it is keyboard- and screen-reader-operable without a single
  `onClick` handler on a div.
- **Import from LinkedIn (Coming soon).** Rendered, inert, `aria-disabled`.
  This is a **deliberate exception** to `/sources`' rule that a greyed
  "coming soon" card is an advert on a page someone came to work on (doc 12).
  Onboarding is the one screen where the user is choosing _how_ to start, and
  "the other way is coming" is the answer to "is this all there is?". The
  eventual implementation is doc 12's `file` auth mode — a LinkedIn data export
  — routed through the existing staging pipeline rather than through this flow.
- **Skip, rendered in every state and disabled while work is in flight.** A real
  exit, not a cancel: it marks the flag, leaves the seeded draft alone, and goes
  to `/profile`. Because it is not a cancel, pressing it mid-scan would start a
  navigation while a fetch is still running, and the user could not say which of
  the two decided what their profile contains — so the screen only ever does one
  thing at a time. The cost is real and accepted: someone who changes their mind
  eight seconds into a twenty-second scan waits for it to finish. It stays
  _rendered_ while disabled, because a control that vanishes reads as the product
  having taken the choice away where a greyed one reads as "not right now", and a
  failed or empty scan returns to the first step with everything enabled.
  **`busy` is derived** from the stage and the transition rather than tracked as
  its own flag, so a new stage cannot leave a control live by omission — and
  `disabled` is kept separate from `pending`, since a spinner on Skip during a
  scan would claim the skip is running.

**The upload card does not render when AI is unavailable** (`isAiAvailable()` —
the same `AI_ENABLED` + credential pair every AI route checks). A card that opens
a file picker and then answers 501 is worse than one that was never offered. The
route refuses independently: a hidden control is never the only guard.

### 5. Extraction: one route, one action, two real phases

```
POST /api/onboarding/resume   →  reads the PDF, returns a Profile. Writes nothing.
applyResumeImportAction       →  stores it. A Server Action a human clicked.
```

**Why a route handler.** Doc 13's test is that a route exists only where a stream
is the product requirement. This one earns its exception on the _other_ rule the
repository already recognises, stated in `/api/uploads/route.ts`: a Server Action
serialises its arguments, and pushing a multi-megabyte binary through that path
is neither efficient nor bounded — the action body limit is 1MB by default, and
raising it raises it for every action in the app.

**Why the write is still an action.** Doc 13's spine is propose → review →
apply, and onboarding is not an exception to it. The extraction is a model
reading a document; the user sees what it understood before their profile becomes
it. That the draft being replaced is only the seed does not make replacing it
without consent a better idea — and the review screen is also the only place a
bad extraction can be caught before it is discovered later in an editor full of
someone else's phrasing.

**Why two phases and not five.** Two network round trips exist, so the loading
sequence has two phases (`scanning`, then `building`), each with its own status
bank. Everything else a premium loading sequence would want to show —
"structuring", "mapping to your profile", "3 of 5" — would be invented:
`generateObject` emits nothing at all until it is finished. Doc 13's "no fake
progress" applies here with _more_ force than anywhere else, because this is the
one wait long enough that a progress bar would be convincing. The screen shows a
scan line over a skeleton page, which claims activity and nothing else. The page
deliberately does **not** fill in behind the line: revealing rows as it passes
looked considerably better and read as "we have now understood these three
lines", against a call that had returned nothing.

**The PDF goes to the model as a file part, not as extracted text.** No PDF
parsing dependency is added. The provider's own document handling reads page
layout, which is what a two-column résumé needs, and degrades to reading a
scanned page as an image — where a text-extraction library returns nothing at
all. The bytes live in memory for the length of the call and are **never
stored**: nothing reaches R2, no `assets` row is written. The file the user chose
is not something Resfolio keeps.

### 6. The extraction contract lives in `@resfolio/profile`

`domains/profile/src/intake.ts`: the model-facing `resumeExtractionSchema` and
the pure `buildProfileFromResume`. Beside `proposal.ts`, for the same reason —
nothing in it is model-facing. It declares a shape, sanitises values and builds a
`Profile` through the package's own schemas. No SDK, no provider, no prompt;
those stay in `apps/dashboard/lib/ai/`, and the tests need no model.

**Not `@resfolio/integrations`, and the reason is structural.** Doc 12's central
rule is that _a connector may never propose the user's identity_ — no candidate
kind carries `name`/`summary`/`location`, and `basics` is not a route target. A
résumé **is** the user's identity: the name, the summary and the contact block are
most of the value. Modelling this as a connector would have required breaking that
rule, which is enforced by absent fields precisely so it cannot be broken by
accident.

#### Why this may add content when `proposal.ts` may not

`proposal.ts` has no "add" variant, because a model proposing a new role is
inventing a job. Here adding _is_ the operation. The invariant that replaces "no
adding" is **nothing may be produced that the document did not contain**, and it
rests on five properties:

1. **Transcription, not authorship.** Every field is copied prose or a copied
   fact. There is no field for a rewritten summary, an inferred seniority, or an
   implied skill — the prompt asks for that too, but the schema is what leaves an
   embellishment nowhere to go.
2. **Every item re-parses through the section's own Zod schema.** The
   `richTextSchema` that rejects raw HTML from a keyboard rejects it from a PDF.
   Model output is hostile input and is not privileged (doc 10).
3. **A bad item is dropped, never repaired into something else, and never
   fatal.** One unreadable date in a five-role résumé must not cost the other
   four roles, so fragile _fields_ normalise to absent and only a genuinely empty
   required field drops the item.
4. **Counts come from the built Profile, not from the extraction.** A screen
   saying "5 roles" over a profile holding 4 is worse than one saying 4 — the
   same rule that makes `proposal.ts` show the schema-normalised value in a diff.
   `dropped` is surfaced too: it is the only place a user learns the document had
   more in it than this.
5. **Every item carries `source: "resume"`.** A new `ItemSource`, not `manual`,
   because nobody typed it — an item that reads oddly is a transcription to check
   rather than a sentence the user stands behind.

Two normalisers are worth naming because they are where silent data loss would
otherwise happen. `calendarDate` recovers "Jan 2020" and "03/2020" but **never
invents a component it was not given** — a bare year stays a bare year, and
anything unreadable becomes absent rather than approximate, because a wrong date
on a résumé is a worse failure than a missing one. And a bulleted summary is
converted to sentences rather than dropped: `inlineRichTextSchema` forbids lists
in `basics.summary`, and résumé summaries are very often three bullets, so the
alternative is silently losing the paragraph every output surface leads with.

### 7. Ceilings

| Limit                        | Value      | Why                                                                             |
| ---------------------------- | ---------- | ------------------------------------------------------------------------------- |
| `MAX_RESUME_BYTES`           | 8MB        | A token bound in byte clothing; past this it is a thesis, not a résumé          |
| `INTAKE_RATE_LIMIT_REQUESTS` | 3 / 10 min | The tightest of the five modes — and the only one a brand-new account can reach |
| `MAX_INTAKE_OUTPUT_TOKENS`   | 16,000     | The one call whose output is a _whole profile_                                  |
| `MAX_INTAKE_ITEMS`           | 20/section | Caps the model-facing schema, so it binds before generation                     |

The file is checked three ways, cheapest first: shape, then size, then declared
type — and then the **bytes**. `File.type` comes from the OS's extension mapping
and is trivially wrong or forged, so `isPdfBytes` verifies the `%PDF-` magic
number. This is the same posture as the image upload route, which re-encodes
rather than trusting `file.type` (doc 07); a PDF cannot be re-encoded, so
verifying the header is what is left.

The route also **closes when first run is over** (409 once the flag is true). Not
a security boundary — it writes nothing and the caller owns everything involved —
but its output exists only to replace a profile wholesale, and `/sources` is the
import path for a profile that already has content in it.

## Tradeoffs

**The extracted Profile round-trips through the browser.** The route returns it,
the client holds it across the review screen, the action stores it. A user could
edit it in flight — and what they would achieve is writing their own profile,
which is what the next screen is for. It is the exact posture
`saveProfileDraftAction` already has, and the action re-parses with
`profileSchema` regardless. What it buys is that the counts the review screen
showed were computed from the _same object_ being stored, so the summary cannot
promise what applying does not deliver.

**One click stands between the extraction and the profile.** The brief was
"pre-fill automatically". The review step is a deliberate deviation, and the
argument is doc 13's: the AI layer never writes without a human trigger, and this
particular write replaces everything. The cost is one click; the benefit is that
a garbled extraction is a "try a different file" rather than a profile the user
has to clean up.

**Sending the whole PDF costs more than sending its text.** A page of scanned
résumé is rasterised and billed as an image. The alternative — `unpdf` or
`pdf-parse` — is cheaper, adds a dependency, gets two-column layouts wrong, and
returns literally nothing for a scanned page, which would fail exactly the users
least able to diagnose why.

**This is a sixth AI call, and it is not yet metered.** Doc 14's spend gate is
built (`@resfolio/billing`) but not wired to any call site; that is the next
task, and résumé intake must be one of the call sites it covers. Until then the
rate limiter is the only ceiling, which is why it is three.

**`custom` sections are not extracted.** A custom section needs a heading the
user chose, and inventing one for "everything else on the page" files
unclassified text under a name nobody picked. Content with no home in the
extraction shape is simply not extracted — the honest outcome, given the editor
is one click away and the résumé is still on the user's disk.

## Future Scalability

- **LinkedIn** is doc 12's `file` mode: the user's data export, normalised by a
  connector, routed and staged through the pipeline that already exists. The
  identity rule means it lands as _content_ — it cannot propose the name.
  Onboarding's card links into that flow rather than growing a second one.
- **A returning-user import** (`/sources` gaining a "from a résumé" source) is
  the same domain function with a different apply path — staged candidates
  instead of a draft replacement. `buildProfileFromResume` is already pure and
  count-reporting, which is what that would need.
- **A second onboarding step** — claim your handle, pick a template — is
  deliberately not here. The flag is a boolean rather than a step index, so
  adding one is a UI change and a schema change, and the schema change is the
  right amount of friction for lengthening the one screen that stands between a
  user and the product.
- **Metering** hooks into the existing `recordAiSpend` gate with `feature:
"resume_intake"`; the free tier's allowance for it is one or two, since it is
  a once-per-account operation.

## Implementation Strategy

Implemented in one pass, 2026-07-30:

1. `ITEM_SOURCES` gains `resume`; `intake.ts` + 32 tests in `@resfolio/profile`.
2. `profiles.onboarding_completed` + migration `0018` (schema, then a
   hand-appended re-runnable backfill).
3. `isOnboardingComplete` / `finishOnboarding` in `@resfolio/profile/server` —
   one upsert behind both exits, bumping `draftRev` on the import path so a stale
   editor tab cannot autosave over an import it never saw.
4. `lib/ai/`: limits, the `intake` rate-limit mode, `resume-intake.ts` (the pure
   upload boundary, 10 tests), `resumeIntakeSystemPrompt`, two status banks.
5. `POST /api/onboarding/resume`.
6. The `(onboarding)` route group, its two actions, and four components.
7. Both halves of the gate.

**Not done: migration `0018` is not applied.** It joins `0003`–`0007`, `0012`,
`0014`–`0017` in the queue for the managed host (doc 15).

**Not done: no e2e coverage.** The flow's two interesting properties are
gate-shaped — a new account cannot reach the dashboard, and a finished one cannot
re-enter onboarding — and both are exactly the kind of thing that regresses
silently, so `e2e/onboarding.spec.ts` should assert them. The upload path itself
needs a fixture PDF and a stubbed route.

## Open Questions

- **Should the review screen show the extracted content, not just counts?** It
  currently shows "3 roles, 2 qualifications, 14 skills" and the name it read.
  Showing the actual entries would make a bad extraction obvious rather than
  merely reportable, at the cost of turning a one-glance screen into a scroll.
  Worth revisiting once there is real data on how often `dropped > 0`.
- **What happens to a user who skips and never fills anything in?** Nothing
  today. A nudge belongs to a lifecycle-messaging design that does not exist yet
  (doc README's deferred transactional email), so this is deliberately open
  rather than half-built.
- **Should a résumé import claim a handle?** The name is right there, and the
  handle is the one remaining setup step. Deferred: a handle is permanent-ish and
  public, and picking one on a user's behalf from a name is exactly the kind of
  identity decision doc 12's rule exists to prevent.

## Alternatives Considered

**A flag on the Better Auth `user` model.** Rejected: the five-minute cookie
cache would make the gate re-fire after completion, and `schema/auth.ts` is
generated. Described in §1.

**Onboarding as a modal over `/profile`.** Cheaper — no route group, no gate —
and it puts a first-run decision on top of the workspace it is meant to precede,
with the sidebar visible behind it. It also has no honest answer to "what does
the page look like while the modal is open", because the answer is a profile full
of placeholder examples.

**A résumé connector in `@resfolio/integrations`.** Rejected on doc 12's
identity rule; described in §6. It would also have put a once-per-account
operation behind a triage workspace built for repeated syncing.

**Client-side PDF parsing (pdf.js in the browser).** Sends less to the server and
keeps the file on the user's machine, which is genuinely attractive. It also ships
a ~400KB parser to every visitor, gets scanned résumés wrong in the one place we
cannot debug, and would still need the extracted text to reach a model — so the
privacy win is smaller than it looks and the cost is real.

**A step-by-step progress bar over the single extraction call.** Rejected on
doc 13's "no fake progress". Described in §5.

---

## Final Recommendation

Ship it as built: a separate route group, a boolean on `profiles` with a
two-sided gate, and a résumé path whose extraction is a read-only route and whose
write is a reviewed Server Action.

The one thing not to compromise later is the review step. Every argument for
removing it is an argument about a click, and the thing it protects against —
someone's profile silently becoming a model's misreading of their own document —
is the failure that would make this feature a liability rather than the fastest
path to a complete Profile.

# 10 — Authentication & Security

Status: Accepted

## Problem Statement

Auth is step one of implementation, and it spans all three apps in
conflicting ways: `apps/dashboard` is fully authenticated, `apps/web` is public
marketing, and `apps/sites` serves public pages that must **never** see a
session — yet also serves private draft-preview and print routes that need
_some_ credential. On top of sign-in, Resfolio hosts user-generated content
on domains we own, so XSS, malicious links, and content injection are
platform risks, not per-feature details. This document decides the Better
Auth setup, the cross-app trust model, and the baseline security posture
every feature inherits.

## Proposed Architecture

### Better Auth in `packages/auth`

Better Auth is configured once in **`@resfolio/auth`** (`packages/auth`):
the server instance (Drizzle adapter over `@resfolio/database`, schema
generated by the Better Auth CLI into our migrations), the typed client
(`createAuthClient`), and small helpers (`requireSession`,
`getOptionalSession`). It mounts in `apps/dashboard` only, at
`app/api/auth/[...all]/route.ts`. Neither `apps/web` nor `apps/sites`
mounts an auth handler at all.

### Sign-in: Google + GitHub social login only (V1)

V1 supports exactly two providers — **Google** (covers Gmail users) and
**GitHub** — and **no email/password**:

- No passwords means no reset flows, no verification emails, no credential
  stuffing surface, and nothing for us to leak. For Resfolio's audience
  (developers and professionals), these two providers cover essentially
  everyone.
- OAuth scopes are minimal: identity + email only. When "GitHub as a
  connected content source" ships later, it uses a **separate** integration
  OAuth flow with its own token storage — login scopes never fatten to serve
  data import.
- Planned fallback for the residual "neither provider" audience: **magic
  links** via Resend (passwordless keeps the no-password property) — an
  additive Better Auth plugin, shipped when demand shows rather than in the
  Phase 2 build (the development plan never scheduled it there). Password
  auth is not planned.

**Account linking**: enabled, keyed on verified email with both providers
trusted (both return provider-verified emails), so one human with a Google
and a GitHub account gets one Resfolio account. Settings exposes
link/unlink; unlinking the last provider is blocked.

### Sessions and the cross-app trust model

- **Database sessions** (Better Auth default) with the **cookie cache**
  enabled (~5 min, signed) so routine requests skip the DB while revocation
  still bites within minutes. Secure, httpOnly, sameSite=lax, **host-only
  cookies on `app.resfolio.me`** — never `domain=.resfolio.me`. Marketing
  and portfolio hosts are structurally session-blind.
- `apps/web` links to the dashboard for login/signup; it never reads
  sessions (a "go to dashboard" navbar state is not worth widening the
  cookie).
- **Portfolio domains are a separate cookie universe.** Public rendering in
  `apps/sites` uses no cookies at all — required anyway for full-page ISR
  caching ([04-deployment](04-deployment.md)), and it makes user-content XSS
  worthless for session theft. This is also why user sites move to
  `*.resfolio.site` rather than `*.resfolio.me` subdomains.

**Route guarding** (defense in depth, DB-free middleware):

1. Middleware on `apps/dashboard` does an _optimistic_ redirect-to-login on
   missing session cookie — UX only, never trusted.
2. The `(dashboard)` layout verifies the session server-side.
3. Every Server Action and Route Handler calls `requireSession` itself via
   the shared action helper ([06-api-architecture](06-api-architecture.md))
   — actions are entry points and never inherit trust from pages.
4. Ownership/authorization stays in `domains/*`, which take the auth context
   explicitly and check `userId` against the resource on every call.

### Signed render tokens (draft preview, print, screenshots)

Private rendering routes on `apps/sites` authenticate with **short-lived
signed tokens**, not sessions: an HMAC-signed payload
`{ profileId, surface: "draft-preview" | "print", exp ≤ 5 min }` minted by
the dashboard (for the preview iframe) or the export job. Print tokens are
additionally **single-use** via the Redis nonce from
[07-storage](07-storage.md). All such routes send `noindex` and are excluded
from ISR caching.

### User-generated content safety

Profile data is hostile input rendered on our domains. Baseline, enforced at
the pipeline level so templates can't opt out:

- **No raw HTML anywhere.** Rich text is the constrained structured subset
  from [01-profile-engine](01-profile-engine.md), rendered by our own
  renderer to React elements — `dangerouslySetInnerHTML` is banned (ESLint
  rule) in templates and apps.
- **URL allowlist**: user-supplied links are validated at the schema layer
  (Zod refinement) to `http/https/mailto` — `javascript:` and `data:` never
  reach storage, and the rich-text renderer re-checks on output.
- **Images** only from our R2/CDN hosts (uploads pipeline,
  [07-storage](07-storage.md)); `next/image` `remotePatterns` is the
  enforcement backstop.
- **CSP on `apps/sites`**: `script-src 'self'`, no inline event handlers,
  `frame-ancestors 'none'` — except the draft-preview route, which allows
  framing by `app.resfolio.me` only. Standard hardening headers
  (`referrer-policy`, `x-content-type-options`, HSTS) on all apps.
- **Rate limiting** (Upstash, per [06](06-api-architecture.md)/[07](07-storage.md)):
  auth endpoints, publish, export, upload presigns, waitlist.

### Secrets and CSRF

- All secrets flow through the validated env package
  ([11-engineering-foundation](11-engineering-foundation.md)); nothing
  secret is ever `NEXT_PUBLIC_*`. OAuth client secrets and the render-token
  HMAC key live only in `apps/dashboard` / `apps/sites` server env respectively.
- CSRF: Better Auth protects its endpoints; Next.js Server Actions enforce
  same-origin; the remaining Route Handlers are webhooks (signature-verified:
  Stripe/Trigger.dev signatures) or token-guarded render routes.

## Tradeoffs

- **Social-only login** excludes users unwilling to use Google/GitHub —
  accepted for V1 (tiny slice of the target audience) with magic links as
  the planned, still-passwordless escape hatch. We also inherit provider
  dependency: a Google OAuth outage blocks logins (not sessions).
- **Cookie cache** means a revoked session can live up to its ~5-minute
  cache window. Acceptable for a dashboard; sensitive actions (billing,
  domain changes, deletion) can force a fresh DB check.
- **Host-only cookies** sacrifice cross-subdomain conveniences (auto-login
  awareness on marketing pages) for a hard tenant-isolation boundary — the
  right trade for a platform hosting arbitrary user content.
- **Tokens instead of sessions for previews** add a minting step, but keep
  `apps/sites` cookie-free and cacheable, and scope each credential to one
  profile + surface + 5 minutes — far smaller blast radius than a session
  cookie in an iframe.

## Future Scalability

- **Magic links** (Resend) and **passkeys** are Better Auth plugins — additive.
- **Teams/organizations**: Better Auth's organization plugin supplies
  membership/invites; authorization stays in domains, which already take an
  explicit auth context ([06](06-api-architecture.md)).
- **Public API auth**: API keys / bearer tokens as a separate credential
  type at extraction time — never dashboard cookies.
- **Connected sources**: separate OAuth integrations table storing encrypted
  provider tokens, isolated from login accounts by design (scopes decision
  above already carved this seam).
- **2FA** for high-value accounts: plugin, post-V1.

## Implementation Strategy

1. `@resfolio/database` + `@resfolio/auth`: Drizzle schema (Better Auth
   generated tables), server instance with Google + GitHub, account linking
   on; `@resfolio/env` for the secrets.
2. Mount in `apps/dashboard`: auth routes, login screen (two buttons, honest and
   small), middleware redirect, `(dashboard)` layout guard,
   `requireSession` in the action helper.
3. Settings → linked accounts (list/link/unlink with last-provider guard).
4. Schema-layer URL validation + rich-text renderer with allowlist (lands
   with the profile schema).
5. Security headers/CSP in both Next configs; render-token helper
   (`packages/auth` or `apps/sites` lib) when the print route ships.
6. Rate limits as each surface lands (auth first).

## Open Questions

- Bot/abuse protection on signup (Cloudflare Turnstile?) — decide at public
  launch; social-only login already raises the bar.
- Account deletion & data export flows (see the deferred-designs list in
  `docs/README.md`) — must exist by public launch; the cascade design is a
  storage concern, the confirmation/grace-period UX is decided here.
- Session lifetime/refresh policy (Better Auth defaults vs. shorter for
  billing-capable accounts) — tune during auth implementation.
- Whether draft-preview tokens are per-iframe-load or refreshed by the
  dashboard on an interval (ties into [09](09-rendering-pipeline.md) open
  question; decide when the iframe ships).

## Alternatives Considered

- **Email/password at launch** — maximum inclusivity, but buys reset flows,
  verification, breach-password checks, and support burden for a user slice
  near zero in this audience. Rejected; magic links are the fallback.
- **NextAuth/Auth.js** — viable, but Better Auth's Drizzle-first schema,
  typed client, and plugin path (organizations, passkeys, API keys) match
  this stack better; it was also the stated stack preference. No reason to
  deviate.
- **Clerk/WorkOS (hosted auth)** — fastest start, but per-MAU pricing at
  "hundreds of thousands of users," a hosted dependency in the middle of the
  product, and our data model already needs the Postgres tables anyway.
  Rejected.
- **JWT-only stateless sessions** — no revocation without an allowlist,
  which reinvents DB sessions. Rejected; DB sessions + cookie cache is the
  same speed with real revocation.
- **Sharing the session cookie across `.resfolio.me`** for marketing-site
  personalization — convenience traded against widening the credential to
  every current and future subdomain. Rejected on principle.

## Final Recommendation

Better Auth configured once in `@resfolio/auth`, mounted only in `apps/dashboard`:
Google + GitHub social login with account linking, no passwords, database
sessions with a short cookie cache, host-only cookies. Public rendering is
cookie-free by construction; private render surfaces use single-purpose
5-minute signed tokens. User content is treated as hostile at the schema,
renderer, and CSP layers simultaneously. Authorization never leaves
`domains/*`. This is the smallest auth surface that covers V1 — and every
planned expansion (magic links, orgs, API keys, 2FA) is an additive plugin,
not a redesign.
